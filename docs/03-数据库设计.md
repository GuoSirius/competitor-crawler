# 03 · 数据库设计

> 本篇回答"**数据怎么存、怎么不重复、怎么增量维护**"。业务诉求（统一存储 / 软删除 / 增量 upsert / 无感切库）映射到具体表结构与索引。技术落地见 `packages/shared/src/db`（Drizzle）。

## 3.1 业务视角：我们要解决什么

| 业务诉求 | 数据库层面的解法 |
|---|---|
| 同一竞品在不同品类下可能出现同名/同 SKU 产品 | 用 `(company_id, dedupe_key, section_key)` 组合唯一索引锁定，杜绝重复 |
| 同一 SKU 在不同**栏目**详情内容确实不同（如「全部产品」与「促销」） | 去重口径 B：`section_key` 并入去重键，**同 SKU 分栏目分开为两条**（见 3.4） |
| 产品会上下架、价格会变 | 物理不删，**软删除**（状态位）+ 历史 `last_seen_at`，季度增量比对 |
| 竞品清单（Excel）会增删改 | 种子增量同步：公司按 `name` upsert；品类按 `(公司, 产品线, 品类名)` 业务主键；消失行软标记 `removed_at` |
| 异构页面字段可能突变 | 统一结构存核心字段，其余全量兜底进 `row` JSON，突变可追溯 |
| 后期换 MySQL / PG | 全部走 Drizzle ORM，方言切换不改业务代码（见 09） |
| 想知道"这次爬了什么、改了什么" | `crawls` 批次表 + `alerts` 告警表，全过程可审计 |

**核心不变量**：一个真实产品 = `(company_id, dedupe_key, section_key)` 唯一；`dedupe_key = COALESCE(source_product_id, canonical(detail_url))`，`section_key` 标识它来自哪个栏目（单规则站点统一为 `'default'`）。只要这条成立，任何来源的重复数据都会落到同一行（upsert），不会出现"同产品两行"；而"同 SKU 出现在不同栏目"按口径 B 有意分列两行（见 3.4）。

## 3.2 实体关系

```
companies 1 ──< categories 1 ──< products
   │                                │  │
   │                                │  └──< price_history >── crawls
   └──────────── 1 ────< crawls 1 ──< alerts

companies     : 竞对公司（Abcam / CST / 义翘神州 …）
categories    : 品类（公司 + 产品线 + 品类名 + 品类链接，对应 Excel 一行）
products      : 产品（归一化后的统一结构 + row 兜底）
price_history : 价格时序（仅记录价格变化点，供后期做价格走势 / 涨跌告警）
crawls        : 每次爬取批次（谁触发、跑了多久、产出了多少）
alerts        : 本次爬取产生的告警（缺失 / 变化 / 突变 / 不可达 …）
```

## 3.3 表结构（Drizzle 定义 + 字段语义）

> 以下以 Drizzle `sqliteTable` 语法示意，MySQL/PG 仅类型映射不同（见 9.2），结构一致。

### 3.3.1 companies — 竞对公司

```ts
export const companies = sqliteTable('companies', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  name: text('name').notNull().unique(),          // 业务主键：Abcam / CST
  website: text('website'),                        // 规范化主域名，便于按域名路由适配器
  competitorType: text('competitor_type'),         // 竞对类型：抗体厂商 / 细胞试剂 / 血清 …
  sourceRow: text('source_row', { mode: 'json' }), // Excel 原始行，便于追溯
  removedAt: integer('removed_at'),                // 软删除：Excel 中整行消失时打标
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
});
```

### 3.3.2 categories — 品类（Excel 一行）

```ts
export const categories = sqliteTable('categories', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  companyId: integer('company_id').notNull().references(() => companies.id),
  productLine: text('product_line'),               // 产品线：抗体 / ELISA / 流式 / 细胞 …
  name: text('name').notNull(),                    // 品类名：Primary Antibodies …
  url: text('url').notNull(),                      // 竞品品类链接（种子 URL）
  sourceRow: text('source_row', { mode: 'json' }),
  removedAt: integer('removed_at'),                // 种子同步时该行消失 → 打标，停止刷新
  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
}, (t) => ({
  // 业务主键：同一公司下的「产品线 + 品类名」唯一
  uniqCat: uniqueIndex('uniq_cat').on(t.companyId, t.productLine, t.name),
}));
```

### 3.3.3 products — 产品（归一化 + 兜底）

字段分四层（判据：**要跨站点比价 / 报告筛选 / 排序 → 拍成列；仅单站点特有 → 留在 `row` JSON**）：

| 层 | 字段 |
|---|---|
| ① 身份 | `companyId` / `categoryId` / `sectionKey` / `dedupeKey` / `sourceProductId` / `sku` / `name` / `detailUrl` |
| ② 可比 | `price` / `currency` / `priceText` / `specText` / `brand` / `englishName` |
| ③ 描述 | `description`（纯文本）、`introMedia`（图文富文本） |
| ④ 扩展 | `row`(J) 原始快照兜底、`specs`(J) 多规格价、`applications`(J) 应用、`cloneNumber` 克隆号 |

```ts
export const products = sqliteTable('products', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  companyId: integer('company_id').notNull().references(() => companies.id),
  categoryId: integer('category_id').references(() => categories.id),

  sourceProductId: text('source_product_id'),      // 站点自身产品 id：有则写、无则留空（⚠️ 不用货号兜底，见 3.4）
  sku: text('sku'),                                // 货号（catalog no.）：有则必写、无则空；用于跨公司对齐/比价
  dedupeKey: text('dedupe_key').notNull(),         // COALESCE(source_product_id, canonical(detail_url))
  sectionKey: text('section_key').notNull().default('default'), // 栏目维度（去重口径 B）；单规则站点统一 'default'

  name: text('name'),
  englishName: text('english_name'),               // 英文名（生物试剂普遍中英文双名）
  brand: text('brand'),                            // 品牌（同公司可能多品牌）
  detailUrl: text('detail_url'),

  price: real('price'),                            // 价格数值（默认规格价），排序/涨跌计算用
  currency: text('currency'),                      // 币种（站点级，缺省 CNY）
  priceText: text('price_text'),                   // 价格原文保真（如「￥1,280.00 / 100μL」）
  specText: text('spec_text'),                     // 规格原文（如 100μL）；比价必须同规格
  description: text('description'),                // 纯文本描述

  specs: text('specs', { mode: 'json' }),          // 多规格明细 [{ spec, priceNow, priceActivity, pricePromo }]
  introMedia: text('intro_media', { mode: 'json' }),// [{ image, description }]
  cloneNumber: text('clone_number'),
  applications: text('applications', { mode: 'json' }),

  row: text('row', { mode: 'json' }),              // 详情页其余所有信息，全量兜底（站点特有属性放这）

  status: text('status').notNull().default('active'), // active | delisted（软删除）
  firstSeenAt: integer('first_seen_at').notNull(),
  lastSeenAt: integer('last_seen_at').notNull(),
  missingSince: integer('missing_since'),          // 首次"本轮未再见"的时间戳；连续 2 轮才 delisted

  createdAt: integer('created_at').notNull(),
  updatedAt: integer('updated_at').notNull(),
}, (t) => ({
  // ★ 组合唯一索引：一个产品在公司内、按栏目唯一（去重口径 B）
  uniqProduct: uniqueIndex('uniq_product').on(t.companyId, t.dedupeKey, t.sectionKey),
  // 常用查询加速
  idxCompanyCatStatus: index('idx_company_cat_status').on(t.companyId, t.categoryId, t.status),
  idxCompanySku: index('idx_company_sku').on(t.companyId, t.sku),   // 按货号查（同公司内对齐）
}));
```

**字段填值口径**（crawl 落库时统一执行，`packages/crawler/src/commands/crawl.ts`）：

| 字段 | 规则 |
|---|---|
| `sku` | 货号，抓到就写；抓不到留 null。**必须从详情页或列表页任一处取到即可** |
| `sourceProductId` | 只装站点自身产品 id；抓不到留 null。**绝不用货号兜底**（理由见 3.4） |
| `dedupeKey` | `COALESCE(sourceProductId, canonical(detailUrl))` —— 货号不参与 |
| `price` / `priceText` | 数值列用于排序，原文列保真；详情页缺价格时用**列表页价格兜底** |
| `specText` | 详情页缺规格时用列表页规格兜底 |
| `currency` | 站点级配置（`config/sites/<domain>.yaml` 的 `currency`），缺省 `CNY` |

> **「详情优先、列表兜底」**：列表页往往有货号/规格/价格，而详情页反而缺；故列表阶段抽取的字段随 `ListItem.raw` 带下去，落库时以详情值优先、列表值补空。

### 3.3.4 price_history — 价格时序

```ts
export const priceHistory = sqliteTable('price_history', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  productId: integer('product_id').notNull().references(() => products.id),
  price: real('price'),                    // 本次抓到的价格数值（可能为空：页面未展示）
  currency: text('currency'),
  priceText: text('price_text'),
  specText: text('spec_text'),             // 规格快照（比价须同规格）
  crawlId: integer('crawl_id').references(() => crawls.id),
  capturedAt: integer('captured_at').notNull(),
}, (t) => ({
  idxProductTime: index('idx_price_history_product_time').on(t.productId, t.capturedAt),
}));
```

- **写入口径**：每轮 crawl 中，该产品**首次入库**或**价格发生变化**时追加一行（新旧价格全空则不记）。同一价格不会重复堆积。
- **当前状态**：**只写入、不消费**。消费端（价格走势报告 / 涨跌告警）待后续接入，不影响现有逻辑。
- **与 `specs` 的关系**：`specs`(JSON) 存**多规格明细价**，本表存**默认规格价的时序**，二者并存互补。

### 3.3.5 crawls — 爬取批次

```ts
export const crawls = sqliteTable('crawls', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  trigger: text('trigger').notNull(),              // schedule | manual
  status: text('status').notNull(),               // running | success | partial | failed
  modelMode: text('model_mode'),                   // 本次使用的模型模式 local/cloud/hybrid
  summary: text('summary', { mode: 'json' }),      // { companies, categories, new, updated, delisted, alerts }
  startedAt: integer('started_at').notNull(),
  finishedAt: integer('finished_at'),
});
```

### 3.3.6 alerts — 告警

```ts
export const alerts = sqliteTable('alerts', {
  id: integer('id').primaryKey({ autoIncrement: true }),
  crawlId: integer('crawl_id').references(() => crawls.id),
  type: text('type').notNull(),                    // MISSING_FIELD | FIELD_CHANGED | BULK_DRIFT | SITE_UNREACHABLE | NEEDS_API_HINT
  severity: text('severity').notNull(),            // info | warning | error
  companyId: integer('company_id').references(() => companies.id),
  categoryId: integer('category_id').references(() => categories.id),
  productId: integer('product_id').references(() => products.id),
  message: text('message').notNull(),
  payload: text('payload', { mode: 'json' }),      // 结构化细节（旧值/新值/样本）
  status: text('status').notNull().default('open'),// open | ack | resolved | auto_fixed
  createdAt: integer('created_at').notNull(),
});
```

## 3.4 组合唯一索引详解（★核心）

```sql
CREATE UNIQUE INDEX uniq_product ON products(company_id, dedupe_key, section_key);
```

- **为什么用组合而非单 `source_product_id`**：很多站点详情页没有暴露稳定产品 id，此时退化为 `canonical(detail_url)`（去掉 query/trailing slash/锚点）。两者取其一作为 `dedupe_key`，保证在"有站点 id 用 id、无 id 用 URL"下都不重复。
- **⚠️ 货号（`sku`）为什么不参与去重**：去重键必须表达**页面级**唯一性，而货号是**产品级**唯一。生物试剂里同一货号常对应多张规格页（如 `ZQ1273` 的 100μL 与 1mL 各自成页、各有独立 URL），拿货号当去重键会把它们**误合并成一条、造成数据丢失**。因此：
  - `source_product_id` **只装站点自身产品 id**，抓不到就留空，**绝不用货号兜底**；
  - `sku` 是独立的业务列，用途是**跨公司对齐 / 比价**（报告层），不参与任何去重。
- **`canonical(detail_url)` 规则**：`toLowerCase()` → 去 `?utm_*` 等追踪参数 → 去 `#` 锚点 → 去末尾 `/`。规则集中在 `packages/shared/src/url.ts` 一个函数，站点间共用。
- **列表阶段就先去重（同一页内的重复链接）**：不少列表页把同一产品渲染**两次**——`<div class="pc">` + `<div class="web">` 双套模板，或同一条目里「图片链接」+「标题链接」两个 `<a>`。若不去重，同一详情会被**抓两次**（纯浪费），`新增` 计数还会**虚高**（日志报 16、库里只有 8）。故 `crawl` 在进入详情阶段前，先按 `canonical(detail_url)` 对列表条目去重（`packages/crawler/src/fetch/listDedupe.ts` 的 `dedupeListItems`，保留首个出现者），落库前再按 `dedupe_key` 唯一化（`uniqueBy`）——**与 upsert 的冲突口径完全一致**，不改变任何落库语义。
- **`section_key` 的引入（去重口径 B）**：同一 SKU 可能同时出现在两个栏目（如某站"全部产品"和"促销"两个列表页）。若二者详情内容确实不同，需要**分开为两条**，故把 `section_key` 并入去重键。单规则站点所有产品 `section_key` 均为 `'default'`，行为与旧版一致（等价于原来的 `(company_id, dedupe_key)`）。
- **冲突即 upsert**：写入时 `ON CONFLICT(company_id, dedupe_key, section_key) DO UPDATE`，所有可比对字段更新，并刷新 `last_seen_at` / `updated_at`。
- **跨品类同名**：同一产品可能同时出现在两个 *品类*(category)，组合键含 `company_id` + `section_key` 但不含 `category_id`，因此落到同一行；`category_id` 以"最近一次归属"记录即可（或允许一对多，见 9.4 扩展）。
- **为什么要 `section_key` 而不用 `category_id` 去重**：`category` 是种子来源的品类（Excel 一行），`section` 是**抓取规则维度**（站点栏目）。同一品类下也可能并列多个栏目、规则各异（见 05.7），用 `section_key` 才能精确表达"同一 SKU 因栏目不同而分列"。

## 3.5 软删除与增量维护

### 3.5.1 产品软删除（连续 2 轮缺失才下架）

> 防止单次网络抖动 / 临时缺页误删。

```
本轮爬取结束：
  for each 已知 active 产品 p:
     若 p 在本轮"应爬范围"内但未被再次见到：
        若 p.missingSince 为空 → 置 missingSince = now，仍 active
        否则 → status = 'delisted'，清空 missingSince（保留全部数据，物理不删）

本轮新见到 p（无论之前 missing 还是 delisted）：
     status = 'active'，missingSince = null，lastSeenAt = now
```

- 下游查询默认 `WHERE status='active'`；历史/下架分析可放宽。
- 数据永不清空：`specs / introMedia / row` 保留，便于"下架前最后一次快照"追溯。

### 3.5.2 种子增量同步（Excel 增删改）

```
加载 标准 seeds.json（由 scripts/xlsx-to-seeds 产出）
① companies：按 name upsert。新公司插入；老公司字段更新。
   若某公司在新种子中不存在 → removedAt = now（停止刷新其品类/产品，历史数据保留）。
② categories：按 (company_id, product_line, name) 业务主键 upsert。
   若某品类在新种子中不存在 → removedAt = now（不再爬，但其历史产品保留）。
③ 记录本轮种子指纹，便于下次 diff（哪些品类是新增/移除）。
```

- Excel 行"消失" ≠ 产品下架：前者是**种子源**变化（我们不再主动去爬这个品类），后者是**官网**产品下架。两者分属 `categories.removedAt` 与 `products.status`，互不混淆。

## 3.6 翻页三策略在 DB 以外的落地说明

翻页属于 Fetch / Adapter 层逻辑（见 05），但产物（多页产品列表）最终都归一化进 `products`，对数据库透明。三种策略：

| 策略 | 触发方式（默认 UI 驱动） | 何时可优化为接口 |
|---|---|---|
| `pagination-html` | Playwright 点击页码 → 整页重渲染 → cheerio 解析 | 稳定、无签名、整页可预测时可选 |
| `pagination-api` | 点击触发 XHR，Playwright 监听 network 取 JSON（可选） | 同左，且接口稳定 |
| `scroll-api` | Playwright 滚动到底 → 等待新节点（无限滚动） | 稳定无签名时可直接调滚动接口 |

> 原则（见 02 设计原则与用户最新要求）：**抓取默认用浏览器渲染内容，不主动逆向接口**；接口逆向仅作为"稳定、无签名、无风控"站点的性能优化，且一旦该站启用接口模式失败，自动回退 UI 驱动。找不到翻页接口时发 `NEEDS_API_HINT` 告警（见 07）。

## 3.7 索引与性能建议

- 必建：`uniq_product`、`uniq_cat`、`companies(name)`、`products(company_id, category_id, status)`。
- 已建辅助：`products(company_id, sku)`（按货号对齐）、`price_history(product_id, captured_at)`（价格时序）。
- SQLite 本地：季度跑一次，量级为「106 品类 × 数百~数千产品」≈ 十万级以内，索引足够。
- 切生产库后：对 `products(row)` 大 JSON 列视库而定（MySQL 用 `JSON` 类型、PG 用 `jsonb` 并可加 GIN）；历史归档可按月分区（见 09.4）。

## 3.9 字段晋升与 row 回填（后期演进）

`row` 兜底保证了"今天没想到的字段明天也能从 `row` 里挖出来"。但频繁查询的字段一直走 `row->>'key'` 解析，既慢又不直观。当某字段被确认"重要 / 高频使用"时，可**晋升为独立列**，流程如下（统一、可回滚、幂等）：

### 流程四步

1. **改 schema 加列**：在 `packages/shared/src/db/schema.ts` 的 `products` 表新增列，如 `cloneNumber: text('clone_number')`。
   - 列定义与现有字段风格一致（物理列 snake_case、TS 字段 camelCase）。
2. **迁移（唯一入口）**：`pnpm db:push`（drizzle-kit push，diff 式，幂等）。
   - 绝不散写 ALTER SQL；SQLite 下自动 `ALTER TABLE ADD COLUMN`，无数据丢失。
   - 生产切 MySQL/PG 时，同一套 schema + 对应方言 push，业务代码不变（见 09）。
3. **回填历史数据**：`pnpm backfill --column clone_number --row-key "Clone Number" --dry` 先统计，确认后去掉 `--dry` 正式回填（见 10.4 / 11）。
   - 回填脚本仅写"目标列为空且 `row` 中确有该 key"的行，**幂等可反复跑**。
4. **接入写入路径**：在适配器 / normalizer 中把该字段声明进 `parseDetail.fields`（如 `cloneNumber: { sel: ..., text: true }`），写入时落到新列；`row` 仍保留全量（`captureRest`），**零数据丢失**。
   - 之后该字段查询直接读列（快、类型明确），不再解析 `row`。

### 一致性约定
- **迁移** 只用 `db:push`，不手写迁移 SQL；**回填** 只用 `backfill` 命令；二者均在变更记录里体现，便于追溯。
- 新列一旦晋升，建议在本文对应字段表补一行说明，保持文档与代码一致。
- **唯一例外：货号（`sku`）不参与去重**。晋升为列是为了「跨公司对齐 / 比价」，而**不是**为了当去重键——理由见 3.4（货号是产品级唯一，同货号可对应多张规格页）。

> **实践记录（2026-09-23 · V1 字段晋升）**：一次真实晋升，可作为模板——
> `sku / englishName / brand / price / currency / priceText / specText / description` 8 个字段从 `row` 晋升为独立列，
> 同时新增 `price_history` 表。全流程 = 改 schema → `pnpm db:push` → 适配器 `parseDetail.fields` 声明字段名 → `crawl` 落库映射 → 本文更新。
> `row` 仍保留全量原始快照，**零数据丢失**。

## 3.8 与下游的接口

- **导出 Excel / 图表 / 应用页**：全部基于 `products`（活跃/`row` 兜底）+ `alerts` + `crawls.summary` 视图，详见 08。
- **分析维度天然可下钻**：`company → category → product`，配合 `status`、`specs.price*`、`applications` 等字段即可做对标与趋势。
