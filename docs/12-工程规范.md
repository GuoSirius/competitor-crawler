# 12 · 工程规范与约定

> 本文件沉淀本项目的**跨任务工程纪律**，供你、同事与其他 AI 协作时统一遵守。随项目演进持续补充。

## 12.1 数据库操作必须幂等
- 所有写库操作可重复执行、结果一致：种子同步用 upsert（按业务主键），crawl 用 `ON CONFLICT` upsert，下架走软删除（不物理删），`backfill` 仅填「目标列为空且 row 确有该 key」的行（可反复跑）。
- 迁移统一走 `pnpm db:push`（drizzle-kit，diff 式，天然幂等），**绝不散写 ALTER SQL**。
- 任何新增写库脚本，先自问「跑两遍结果是否一样」，再落地。

## 12.2 优先复用现有 npm 包，不重复造轮子
- 已有且应继续复用的：Drizzle ORM（DB）、better-sqlite3（本地驱动）、cheerio（SSR 解析）、Playwright（SPA 渲染）、yaml（配置）、openai（模型调用）、dayjs（**所有时间处理**，禁裸 `new Date()`）、p-limit（并发控制）、ExcelJS（Excel）、standard-version（版本/CHANGELOG）。
- 新增能力前先确认是否有现成包；微型胶水代码（如单行进度 `Progress`、极简参数解析 `parseFlags`）允许保留，但任何 substantial 功能优先用包。
- 新增依赖：写进对应 `package.json`，由你执行 `pnpm install`（AI 不代装/代启）。

## 12.3 提交规范（commitlint）
- 提交信息遵循 Conventional Commits，由 commitlint 校验（配置 `.commitlintrc.json`，hook 在 `.git/cph/commit-msg`）。
- 本机 husky 不生效，统一 `git commit -c core.hooksPath=.git/cph -m "type: 简述"`。
- type：feat / fix / docs / refactor / perf / test / chore。依赖安装后提交自动校验。

## 12.4 文档与代码一致性
- 改代码/配置必须同步对应文档（脚本清单见 docs/11，规范见本文）。
- 文档放 `docs/` 按主题拆分，根 `README.md` 只做总览 + 导航。
- 重要说明落盘到文档/MEMORY，不只在对话框里（易丢失、难复用）。

## 12.5 验证优先、GFW 友好
- 新增/改站点：先 `pnpm probe` 单站抽样验证，确认解析正确再批量 `crawl`。
- 开发/验证阶段优先选用**中国大陆可直连**的站点做测试对象，避免依赖 VPN；海外站点可临时标 `proxy: required` 或本地开 VPN 单站 `probe`。

## 12.6 脚本单一真相源 + 单脚本参数化
- 全部可执行脚本统一登记在 [11-脚本命令手册](11-脚本命令手册.md)；新增脚本必须同步更新该文并在根 `package.json` 加入口（避免 `cd` 切换目录）。
- **脚本尽量单一、参数化**：避免一堆 `--flag` 变体（如 `release` 只留一个，运行时选/传 patch|minor|major），不重复造多个近义脚本。
- 发布时版本号更新覆盖**所有含版本号文件**（见 `.versionrc.json` 的 `bumpFiles`），新增包须同步登记。

## 12.7 第三方包配置独立成文件
- `package.json` 只放常规配置（name / version / private / type / engines / scripts / dependencies）。
- 第三方包的配置用其**官方推荐的独立配置文件**：standard-version → `.versionrc.json`、commitlint → `.commitlintrc.json`、ESLint → `eslint.config.*`、Prettier → `.prettierrc` 等。不把工具配置塞进 package.json。
