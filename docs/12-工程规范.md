# 12 · 工程规范与约定

> 本文件沉淀本项目的**跨任务工程纪律**，供你、同事与其他 AI 协作时统一遵守。随项目演进持续补充。

## 12.1 数据库操作必须幂等
- 所有写库操作可重复执行、结果一致：种子同步用 upsert（按业务主键），crawl 用 `ON CONFLICT` upsert，下架走软删除（不物理删），`backfill` 仅填「目标列为空且 row 确有该 key」的行（可反复跑）。
- 迁移统一走 `pnpm db:push`（drizzle-kit，diff 式，天然幂等），**绝不散写 ALTER SQL**。
- 任何新增写库脚本，先自问「跑两遍结果是否一样」，再落地。

## 12.2 优先复用现有 npm 包，不重复造轮子
- 已有且应继续复用的：Drizzle ORM（DB）、better-sqlite3（本地驱动）、cheerio（SSR 解析）、Playwright（SPA 渲染）、yaml（配置）、openai（模型调用）、dayjs（**所有时间处理**，禁裸 `new Date()`）、p-limit（并发控制）、ExcelJS（Excel）、standard-version（版本/CHANGELOG）。
- 新增能力前先确认是否有现成包；微型胶水代码（如单行进度 `Progress`、极简参数解析 `parseFlags`）允许保留，但任何 substantial 功能优先用包。
- 新增依赖：写进对应 `package.json`，由你执行 `pnpm install`（AI 不代装/代启）。

## 12.3 提交规范（commitlint + 提交前门禁）
- 提交信息遵循 Conventional Commits，由 commitlint 校验（配置 `.commitlintrc.json`）。
- **两条硬约束**（本机踩过，2026-09-23 固化）：
  1. `type` 必须是标准枚举 `build|chore|ci|docs|feat|fix|perf|refactor|revert|style|test`——**没有 `config`**，站点配置类改动统一用 `chore(sites)`。
  2. **主题不能以大写单词开头**（`feat(shared): FieldSpec 支持…` 会被 `subject-case` 判为 sentence-case 而拒绝）→ 主题以**中文或小写词**开头，如 `feat(shared): 为 FieldSpec 增加…`。
- **提交前门禁（pre-commit）**：`pnpm typecheck`（shared + crawler）+ `pnpm test`（单测）**全绿才允许提交**；任一失败即阻止提交。
- 门禁逻辑单一真相源：`scripts/precommit.mjs` / `scripts/commitmsg.mjs`。钩子文件只留一行 `node scripts/*.mjs`（**PATH 无关**——本机钩子进程 PATH 取自系统环境变量，曾出现 `/usr/bin/env: 'sh': No such file or directory`）。
- 两种提交方式，**门禁强度完全相同**（都调同一份 node 脚本）：
  - ① **husky（首选）**：`.husky/` 版本化，`pnpm install` 时由 `prepare` 自动启用 → 直接 `git commit`。
  - ② **回退**：`pnpm hooks:install` 写入 `.git/cph/` → `git -c core.hooksPath=.git/cph commit -m "..."`（`-c` 必须紧跟在 `git` 之后）。
- ⚠️ **本地钩子可被 `--no-verify` / `HUSKY=0` 绕过**，属「便利」而非「保障」。**真正的强制校验应在 CI**（见 §12.11）。
- 逃生门：`--no-verify` —— 不推荐、请勿常用。

## 12.10 单元测试的范围与放置位置
- **放置：与源码同目录（co-located）**，命名 `*.test.ts`，即 `packages/<pkg>/src/**/*.test.ts`。
  - 理由：改动源码时测试就在旁边、不易漏更新；IDE 重命名/移动文件会连带测试；相对引用最短不易错；「哪些模块有测试」一眼可见。
  - 前提：本项目 `tsc` 只做 `--noEmit`、用 `tsx` 直跑源码，**无构建产物**，故混写零成本。**若将来真编译（`tsc` 出 `dist/`）**，必须加 `exclude: ["**/*.test.ts"]` 或单独的 `tsconfig.build.json`，避免测试进产物。
- **测试范围（锁定高价值纯逻辑层）**：跨模块/需网络/需 fixture 的集成与端到端测试**另放独立目录**（如 `tests/e2e/`），与单测的「秒级、无需启动」定位区分开；`vitest.config.ts` 的 `include` 需同步扩展。
- 已覆盖：FieldSpec 抽取（文本/attr/regex/list/map/`number`/`$self`/`json+pick`）、形态探测 A~E、`resolveSections`、`pickSectionByUrl`、URL 规范化与去重键。

## 12.4 文档与代码一致性
- 改代码/配置必须同步对应文档（脚本清单见 docs/11，规范见本文）。
- 文档放 `docs/` 按主题拆分，根 `README.md` 只做总览 + 导航。
- 重要说明落盘到文档/MEMORY，不只在对话框里（易丢失、难复用）。

## 12.5 验证优先、GFW 友好
- 新增/改站点：先 `pnpm probe` 单站抽样验证，确认解析正确再批量 `crawl`。
- 开发/验证阶段优先选用**中国大陆可直连**的站点做测试对象，避免依赖 VPN；海外站点可临时标 `proxy: required` 或本地开 VPN 单站 `probe`。

## 12.6 脚本单一真相源 + 单脚本参数化
- 全部可执行脚本统一登记在 [11-脚本命令手册](11-脚本命令手册.md)；新增脚本必须同步更新该文并在根 `package.json` 加入口（避免 `cd` 切换目录）。
- **脚本尽量单一、参数化**：避免一堆 `--flag` 变体（如 `release` 只留一个，运行时选/传 patch|minor|major），不重复造多个近义脚本。
- 发布时版本号更新覆盖**所有含版本号文件**（见 `.versionrc.json` 的 `bumpFiles`），新增包须同步登记。

## 12.7 第三方包配置独立成文件
- `package.json` 只放常规配置（name / version / private / type / engines / scripts / dependencies）。
- 第三方包的配置用其**官方推荐的独立配置文件**：standard-version → `.versionrc.json`、commitlint → `.commitlintrc.json`、ESLint → `eslint.config.*`、Prettier → `.prettierrc` 等。不把工具配置塞进 package.json。

## 12.8 站点配置两种写法（单规则 / 多规则）
- **单规则**（`config/sites/_template.yaml`）：一个域名一套规则，直接写顶层 `startUrl + listTraversal + parseList + parseDetail`。
- **多规则**（`config/sites/_template.sections.yaml`）：一个域名多套规则，写 `sections: [...]`，每栏目自带规则，顶层字段作公共默认值。
- 二者由 `resolveSections()`（`packages/crawler/src/config/loader.ts`）统一归一化为 `ResolvedSection[]`；消费方（probe / crawl）只面向归一化结果，不判断写法。**旧单规则配置零改动兼容**（自动包成 `key='default'`）。
- **去重口径 B**：`products` 唯一键 = `(company_id, dedupe_key, section_key)`；同 SKU 跨栏目分列两条。新增栏目即新增 `section_key`，改名 `key` 等于换去重键，**稳定后勿随意改**（见 03.4 / 05.3.2）。

## 12.11 CI 门禁（本地钩子的真正兜底）—— 已落地
- **问题**：本地 pre-commit 钩子可被 `--no-verify` / `HUSKY=0` 绕过；换电脑/未装依赖时钩子会自动跳过。因此**本地钩子只是便利，不是保障**。
- **方案**：`.github/workflows/ci.yml`，在 `push` / `pull_request` 时跑与本地**等价**的校验：
  ```yaml
  pnpm install --frozen-lockfile   # 严格按 lockfile 安装，依赖漂移即失败
  pnpm typecheck                   # = shared + crawler（web 暂屏蔽，见 §12.9）
  pnpm test                        # = vitest run
  ```
  与本地 `scripts/precommit.mjs` **同源**（该脚本内部就是「tsc shared → tsc crawler → vitest run」三步），故不会出现「本地过、CI 挂」。
- 其它约定：pnpm 固定 `12.5.1`（与本地一致，lockfileVersion 9.0）、Node 24、`concurrency` 取消同分支旧任务。
- 好处：任何人都无法绕过；PR 上可见红/绿；作为第二道保险与本地门禁互为补充。
- ⚠️ 维护点：web 补上 `vue-tsc` 后，此处 `pnpm typecheck` 应同步改为 `pnpm typecheck:all`（见 §12.9）。

## 12.12 工作方式：先做工程对比，再执行（重要）
- 用户提出的建议/方向，**先做工程对比（收益 / 成本 / 风险 / 备选方案）再执行**；发现坑、更优解或方向不成立时，**停下来向用户确认**，不闷头照做。
- 原因：用户可能不了解某些技术的具体后果，按其直觉给出的方向若被机械执行，可能引入静默失败、难以回退的改动或安全隐患。
- 落法：
  - 涉及**新增依赖、改动仓库/工具链配置、修改数据口径、大范围重构、安全相关**的，先出对比表 + 我的推荐 + 明确的决策问题，等用户拍板。
  - 纯实现细节、已有共识的既定事项，直接做（不打断节奏）。
  - 执行中发现的**风险/缺陷/优化点**，随时汇总告知用户，由其决定是否纳入本轮。

## 12.13 环境变量契约（`.env.example` 是唯一真相源）
- **铁律**：代码里 `process.env.XXX` 的键名，**必须以仓库根 `.env.example` 为准**，不得另起名字。历史上出现过「代码读 `OPENAI_API_KEY`，而 `.env` 里写的是 `MODEL_CLOUD_API_KEY`」的缺陷——变量名是字符串，`tsc` 与运行时都看不出错，只在真正调用模型时才暴露，且报错信息完全指不到根因。
- **防复发**：`packages/crawler/src/envContract.test.ts` 做**双向**静态校验：
  1. 代码读取的每个键 → 必须在 `.env.example` 中声明（读而未声明 = 命名写错/臆造）；
  2. `.env.example` 声明的每个键 → 必须有代码读取（声明而未读 = 配置闲置/未接线）。
- **写码约束**：因此**不要**把 env 读取抽象成 `env` 参数（如 `resolveModelConfig(mode, env = process.env)`）——那样静态扫描将看不到键名，防线等于被绕过。需要可测性时，用 vitest 的 `vi.stubEnv()` 注入（见 `llm/client.test.ts`）。
- 扫描器会**先剥离注释**再匹配，故文档注释里可以放心写 `process.env.XXX` 作示例。
- 校验时机：本地 pre-commit（`pnpm test`）+ CI（§12.11）双重拦截。
