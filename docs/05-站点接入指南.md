# 05 · 站点接入指南

> 本篇回答"**每个站列表/详情页都不一样，怎么统一、后期怎么调**"。这是长期维护项目的关键：新增/调整一个站点应尽量只改配置，不动核心代码。

## 5.1 业务视角：为什么要"适配器"

24 个站点、上百个品类页，**结构各不相同**：

- 有的列表整页分页（点页码整页刷新），有的无限滚动（边滚边加载）；
- 有的详情页是静态 HTML（cheerio 可直接解析），有的靠 JS 渲染、甚至有签名/加密/风控接口；
- 字段命名天差地别（"克隆号 / Clone / mAb" 同指一物）。

若把解析逻辑硬写在核心流水线里，每加一个站都要改代码，且一处改版全局受影响。我们用**适配器（Adapter）边界归一化**解决：每个站只产出统一的 `NormalizedProduct`，下游完全不感知差异。

## 5.2 统一接口：SiteAdapter

所有站点实现同一接口，对外屏蔽差异：

```ts
interface SiteAdapter {
  /** 站点域名（用于 Registry 路由） */
  match(url: string): boolean;

  /** 列表遍历：返回该产品品类下全部产品详情页 URL（或带上下文的对象） */
  listTraversal(page: PageHandle): Promise<ListItem[]>;

  /** 解析列表页单条 → 抽取详情页链接 + 基础字段 */
  parseList(node: NodeHandle): ListItem;

  /** 解析详情页 → 归一化产品（含 specs / introMedia / cloneNumber / applications / row） */
  parseDetail(page: PageHandle): NormalizedProduct;
}
```

- `PageHandle` 是 Fetch 层给适配器的"页面句柄"：内部是 Playwright Page（渲染后的 DOM + 截图），对适配器暴露 `html()` / `screenshot()` / `click()` / `scroll()` / `waitFor()`。
- 适配器**不关心**怎么翻页网络细节，只声明"我要点下一页 / 要滚到底"，由 Fetch 层执行。

## 5.3 三类适配器 + 模型通用兜底

| 适配器类型 | 何时用 | 维护成本 |
|---|---|---|
| **配置 YAML 适配器** | 结构稳定、字段位置固定的站点 | 最低：改 `config/sites/*.yaml` 即可 |
| **代码 Adapter** | 结构复杂、需自定义逻辑的站点 | 中：写一个实现 `SiteAdapter` 的类 |
| **模型通用适配器（兜底）** | 以上都搞不定时，直接让模型读页面提取 | 低但耗 token：作为最后手段 |

路由优先级：`YAML 配置` → `代码 Adapter` → `模型通用适配器`。模型兜底保证"没有写适配器的站也不会整轮失败"。

### 5.3.1 配置 YAML 适配器示例

```yaml
# config/sites/abcam.yaml
domain: abcam.com
currency: CNY                    # 站点币种（缺省 CNY）
listTraversal:
  strategy: pagination-html      # 翻页策略（见 5.4）
  nextSelector: "a.pagination-next"
  maxPages: 50
parseList:
  itemSelector: "div.product-card"
  fields:
    detailUrl: { sel: "a.product-link", attr: href }
    name:      { sel: "h3.product-name", text: true }
parseDetail:
  fields:
    name:          { sel: ".pd-name", text: true }
    sku:           { sel: ".catalog-no", text: true }          # 货号（有则必写）
    englishName:   { sel: ".pd-en-name", text: true }
    cloneNumber:   { sel: ".clone-no", text: true }
    applications:  { sel: ".app-list li", list: true }
    price:         { sel: ".price-now", text: true, regex: '[\d,]+\.?\d*', number: true }
    priceText:     { sel: ".price-now", text: true }
    specText:      { sel: ".spec-current", text: true }
    description:   { sel: ".pd-desc", text: true }
    # 规格 × 多种价格（形态 A：每行一个规格）
    specs:         { sel: ".spec-row", list: true,
                     map: { spec:          { sel: ".spec", text: true },
                            priceNow:      { sel: ".price-now", text: true, regex: '[\d,]+\.?\d*' },
                            priceOriginal: { sel: ".price-origin", text: true },
                            priceActivity: { sel: ".price-act", text: true },
                            pricePromo:    { sel: ".price-promo", text: true } } }
    introMedia:    { sel: ".intro-block", list: true,
                     map: { image:       { sel: "img", attr: src },
                            description: { sel: ".intro-desc", text: true } } }
  # 其余未列字段 → 自动全量进 row（兜底）
  captureRest: true
```

- 新增一个"结构规整"的站点：复制模板、改选择器即可，**无需写代码、无需重启（热加载配置）**。
- 配置模板两套（均在 `config/sites/`）：
  - `_template.yaml`：**单规则**穷举示例（本文档示例即此写法）；
  - `_template.sections.yaml`：**多规则（sections）**穷举示例，见 5.3.2。
- `captureRest: true` 保证"页面其余所有信息统一进 `row`"，契合用户"其余全量兜底"要求。
- ⚠️ **FieldSpec 只有两种写法**：`{ sel, text }` 或 `{ sel, attr }`（+ 可选 `regex` / `number` / `list` / `map`）。
  不存在 `sel: ".x"` 这样的字符串简写，也不存在 `"img@src"` 这种 `选择器@属性` 简写——属性必须用 `attr:` 声明。

### 5.3.2 多规则站点：一个域名多套规则（sections）

**问题**：有些站点同一域名下有多个列表页 + 各自的详情页，虽同属一个站点，但**爬取规则不同**（列表卡片结构不同、详情模板不同）。单一 `parseList` / `parseDetail` 无法表达。

**方案**：用 `sections` 数组表达一组栏目，每个栏目自带 `startUrls + match + listTraversal + parseList + parseDetail`；顶层字段作为**公共默认值**供各栏目继承。

```yaml
# config/sites/example.com —— 多规则写法（完整示例见 _template.sections.yaml）
domain: example.com

# 顶层公共默认值（section 未写则继承）
parseDetail:
  fields:
    name: { sel: ".pd-name", text: true }
  captureRest: true

sections:
  - key: all-products                 # 栏目标识：写入 ListItem.sectionKey / products.section_key
    startUrls: ["https://example.com/products"]
    match:                            # 列表/详情 URL 含子串即归属本栏目（供 crawl 反查）
      listUrlIncludes: ["/products"]
      detailUrlIncludes: ["/product/"]
    parseList:                        # 本栏目列表结构
      itemSelector: ".card"
      fields:
        detailUrl: { sel: "a.card-link", attr: href }
        name:      { sel: ".card-title", text: true }
    parseDetail:                      # 本栏目详情模板（不写则继承顶层）
      fields:
        name: { sel: "h1.pd-title", text: true }
      captureRest: true

  - key: promo                        # 促销栏目：只改列表规则，详情/翻页继承顶层
    startUrls: ["https://example.com/promo"]
    match:
      listUrlIncludes: ["/promo"]
      detailUrlIncludes: ["/product/"]
    parseList:
      itemSelector: ".promo-tile"
      fields:
        detailUrl: { sel: "a", attr: href }
        name:      { sel: ".promo-name", text: true }
```

**关键机制**：

| 机制 | 说明 |
|---|---|
| 栏目路由 | 列表阶段给每条 `ListItem` 打 `sectionKey`；详情阶段**按 `sectionKey` 选规则**，零歧义。另提供 `match.listUrlIncludes` / `match.detailUrlIncludes`，用于"拿到未打标的 URL"时按 URL 反查所属栏目 |
| 默认继承 | 优先级：`section 自带值 > 顶层默认值 > 代码内置默认`。多数栏目可只写差异部分 |
| 去重口径 B | 唯一键 = `(company_id, dedupe_key, section_key)`；同 SKU 出现在不同 section 时**分开为两条**（适合"同 SKU 在不同栏目详情内容确实不同"）。单规则站点统一 `'default'`，与旧行为一致（见 03.4） |
| 验证 | `pnpm probe --domain example.com` 逐栏目验证；`--section <key>` 只验证某栏目（见 10.2） |
| 向后兼容 | 不写 `sections` 的旧配置由 `resolveSections` 自动包成 `key='default'` 的单栏目，**无需改动** |

**归一化实现**：`resolveSections(cfg)`（`packages/crawler/src/config/loader.ts`）把两种写法统一成 `ResolvedSection[]`，消费方（probe / crawl）只面向归一化结果，无需判断写法。配置类型见 `packages/crawler/src/config/types.ts`。

### 5.3.3 模型通用适配器（兜底）

当某站没有 YAML / 代码适配器，或既有的突然大面积失效（疑似改版）：
- 抓取页面可见文本 + 截图 → 调模型（见 04 提取契约）→ 输出 `NormalizedProduct`。
- 适合加密/风控/JS 重渲染站（直接读"用户所见"，天然绕开逆向）。
- 代价是 token 消耗；因此作为**兜底**而非首选。

### 5.3.4 规格 × 多种价格：四种形态与抽取手段（★重点）

「一个产品多个规格，每个规格带多种价格（原价 / 活动价 / 优惠价）」是**最容易翻车**的一类结构。务必先判定属于哪种形态，再选手段——否则会出现「spec 抓到了、价格是空的」这类静默缺失。

#### 形态判定（按代价从低到高）

| 形态 | 页面特征 | 数据在哪 | 抽取手段 | 是否需要浏览器点击 |
|---|---|---|---|---|
| **A · 表格行** | 一个 `table` / 一组 `div`，每行一个规格 | DOM 文本 | `list + map` | 否 |
| **B · 下拉项自带属性** | `<select><option data-spec="100μL" data-price="1280">` | 元素的 **attribute** | `list + map` + **`sel: '$self'`** | 否 |
| **C · 内联 JSON / JS 变量** | 页面 `<script>` 里有 `skuList = [{...}]` | `<script>` 文本 | `regex` 抠出 + **`json` + `jsonPath` + `pick`** | 否 |
| **D · 异步接口** | 选中规格后才发 XHR 拿价格 | 网络响应 | **人工提供接口 → 填 `parseDetail.api`**（见下） | ⚠️ 是 |
| **E · 纯前端计算** | 价格 = 基础价 × 系数，前端算出来 | 无稳定来源 | 模型兜底 + `NEEDS_API_HINT` 告警 | ⚠️ 是 |

> **原则**：A / B / C 都是**静态可抽**的（数据已在 HTML 里），优先走配置；**绝不为了 D/E 去主动逆向接口**——先发告警，由人工确认后再决定。
> **如何知道某站属于哪种形态？** 不用人工开页面看：跑 `pnpm probe --domain <domain>`，它会**抽查详情页自动判定形态**并给出结论（见本节末尾「形态自动探测」）。

#### 形态 A：表格行（最常见，现有能力直接支持）

```yaml
parseDetail:
  fields:
    specs:
      sel: "table.price-table tbody tr"      # 每行一个规格
      list: true
      map:
        spec:          { sel: "td:nth-child(1)", text: true }
        priceNow:      { sel: "td:nth-child(2)", text: true, regex: '[\d,]+\.?\d*' }
        priceOriginal: { sel: "td:nth-child(3)", text: true }   # 原价/划线价
        priceActivity: { sel: "td:nth-child(4)", text: true }   # 活动价
        pricePromo:    { sel: "td:nth-child(5)", text: true }   # 优惠价/券后价
```

#### 形态 B：下拉项自带属性（★本次新增 `$self` 支持）

```yaml
parseDetail:
  fields:
    specs:
      sel: "select#spec option"        # 先选出所有 option
      list: true
      map:
        # $self = 读「当前这个 option 自己」的属性（而非它内部的子元素）
        spec:          { sel: "$self", attr: "data-spec" }
        priceNow:      { sel: "$self", attr: "data-price" }
        priceOriginal: { sel: "$self", attr: "data-market-price" }
        priceActivity: { sel: "$self", attr: "data-activity-price" }
        sku:           { sel: "$self", attr: "data-sku" }
```

> `$self` 是唯一能读「被选中元素自身」的方式：`sel` 通常表示「在内部往下找」，而属性恰恰挂在**元素自己**身上。

#### 形态 C：内联 JSON（`json` + `jsonPath` + `pick`）

```yaml
parseDetail:
  fields:
    specs:
      sel: "script"
      text: true
      regex: 'skuList\s*=\s*(\[[\s\S]*?\]);'   # 抠出 JSON 串（优先第 1 捕获组）
      json: true                               # ① 解析成数组/对象（宽松：失败时截取最外层 {}/[] 再试）
      jsonPath: "data.skus"                    # ② 可选：定位到数组所在层级（点号路径，支持数组下标）
      pick:                                    # ③ 站点键 → 我方键
        spec: "specName"
        priceNow: "price"
        priceOriginal: "marketPrice"
```

框架内联状态同样适用（标记常在 `<script>` 的 **id 属性**上）：

```yaml
    specs:
      sel: 'script#__NEXT_DATA__'
      text: true
      json: true
      jsonPath: "props.pageProps.skus"   # 具体路径以实际响应结构为准
      pick: { spec: "name", priceNow: "price" }
```

#### 形态 D：异步接口（人工提供接口 → 填 `parseDetail.api`）★

这一形态**静态 HTML 里没有数据**，必须由人工把接口地址补进配置。**配置位置**：`config/sites/<domain>.yaml` 的 **`parseDetail.api`**（与 `fields` 同级）。

```yaml
parseDetail:
  fields:
    name: { sel: ".pd-name", text: true }
    sku:  { sel: ".catalog-no", text: true }
    # …其余字段保持不动…
  captureRest: true

  # ★ 异步接口数据源：probe 告警后，人工从浏览器 Network 面板找到接口，填在这里
  api:
    - target: specs                             # 结果写回哪个字段：specs / introMedia / 其他名→row
      url: "https://<domain>/api/goods/{sku}/skus"   # {字段名} 用详情页已抽到的字段插值
      method: GET                               # 默认 GET
      headers:                                  # 需要时补 Referer / X-Requested-With 等
        Referer: "https://<domain>/"
      rootPath: "data.list"                     # 从响应里定位数组（点号路径）
      pick:                                     # 站点键 → 我方键
        spec: "specName"
        priceNow: "price"
        priceOriginal: "marketPrice"
```

**`url` 占位符**可用的字段：详情页已抽到的**任意字段**（含内置字段与 `row` 里的键），另有 `{detailUrl}`。
例如 `...?goodsId={sourceProductId}`、`.../{sku}/skus`。若占位符对应字段为空，url 会插值成残缺地址 → 该源报错并跳过（不阻断入库）。

**完整操作流程**（probe 会主动提示）：

```
1. pnpm probe --domain <domain>          # 自动判定形态；D/E 会打印「怎么配」并落 NEEDS_API_HINT 告警
2. 浏览器打开告警里的 sampleUrl → F12 → Network → 勾选 XHR/Fetch
3. 切换一次规格（或刷新），找到返回规格/价格的请求 → 右键 Copy link address
4. 把 URL 填进 config/sites/<domain>.yaml 的 parseDetail.api（见上）
5. pnpm probe --domain <domain>          # 会实测该接口并打印「取到 N 条」+ 样本
6. pnpm crawl --site <domain> --dry-run --limit 3   # 确认无误后再正式采集
```

**可配置多个源**：`api` 是数组，可同时补规格、图文描述、参数表等多个接口。

#### 形态 E：纯前端计算

价格由前端算出来（如 `price × qty`），没有可直接取的数据源。处理顺序：
1. 先按 D 的思路找一个返回**原始价格**的接口（往往存在）填 `parseDetail.api`；
2. 确实没有 → 启用模型兜底适配器（读页面可见文本 + 截图）；
3. 接口存在但被签名/风控保护 → **保持告警**，由人工确认后再决定是否逆向。

#### 形态自动探测（`pnpm probe` 内置）

不用人工逐个开页面判断，probe 会**抽查详情页自动判定形态**（实现：`packages/crawler/src/adapter/shapeDetect.ts`）：

| 判定 | 探测依据 |
|---|---|
| A | 表格中 ≥2 行含价格文本 |
| B | `select > option` 自带属性名命中 `price/规格/货号` 等特征 |
| C | `<script>` 文本或 **id 属性**命中内联 JSON 线索（`skuList`、`__NEXT_DATA__`、`window.__X__`…） |
| D | 存在 `select` / 规格选择元素，但 HTML 里没有静态规格价格数据 |
| E | 在 D 的基础上，脚本里出现价格计算片段（`price * qty`） |
| none | 未发现多规格结构（可能是单规格产品） |

探测结果的处理：

| 形态 | probe 行为 |
|---|---|
| A / B / C | 打印「静态可抽」+ **可直接粘贴的 YAML 片段** |
| D / E | 打印**「在哪配、怎么配」的完整步骤**，并写入 `alerts` 表：`type=NEEDS_API_HINT`、`severity=warning`，`payload` 含 `sampleUrl` / `evidence` / `configFile` / `configPath` / `howTo` |
| 已配 `parseDetail.api` | 跳过形态提示，**实测接口**并打印「取到 N 条」+ 首条样本（这才是「配好了没」的判据） |

- 告警**幂等**：同 `type + message` 的 open 告警不会重复写入（同站反复 probe 不刷屏）。
- 控制探测范围：`pnpm probe --domain <domain> --detail 0` 关闭探测；`--detail 3` 每个栏目抽查 3 个详情页。

**能力状态一览**

| 能力 | 解决的形态 | 状态 |
|---|---|---|
| `list + map` | A | ✅ |
| `sel: '$self'`（读元素自身属性） | B | ✅ |
| `SpecItem.priceOriginal`（原价/划线价） | A / B / C | ✅ |
| `json` + `jsonPath` + `pick` | C | ✅ |
| `parseDetail.api` + JSON 接口抓取 | **D** | ✅ |
| probe 形态自动探测 + 告警 | A~E 判定 | ✅ |
| 模型兜底适配器 | E | ⏳ 未做 |
| `specsViaInteraction`（点选规格读价格） | D（无接口可寻时） | ⏸ 暂不做（原则：不主动逆向接口） |



统一在 `listTraversal.strategy` 声明，Fetch 层据此驱动浏览器：

| 策略 | 行为 | 备注 |
|---|---|---|
| `pagination-html` | 点击页码链接 → 整页重渲染 → 解析 | 最常见，纯 UI 驱动 |
| `pagination-api` | 点击触发 XHR，监听 network 取 JSON（可选优化） | 仅稳定无签名站启用；失败自动回退 html |
| `scroll-api` | 滚动到底加载更多（无限滚动） | 同上，可优化为直接调滚动接口 |
| `model-generic` | 模型读页面判断"有没有下一页/加载更多按钮"并操作 | 极端异构站的兜底 |
| `pagination-url` | 用 **URL 模板**直接拼第 N 页地址（如 `?page={page}` / `&p={page}`）逐页抓取，**不启浏览器** | 适合「整页重渲染、地址栏带页码参数」的 SSR 站；最稳、最省，首选 |

> **用户最新要求落地**：默认**优先用浏览器渲染内容，不主动逆向接口**。接口模式只是可选优化（稳定、无签名、无风控时），且配置 `fallbackToUi: true` 确保失败回退 UI 驱动。定位不到翻页接口时发 `NEEDS_API_HINT` 告警（见 07），由你人工找到后回填，再告知系统。

#### `pagination-url` 详解（★ 本次新增）

部分站点（多为 SSR / PHP 站）翻页是**纯 URL 参数驱动**：点击下一页只是把地址栏从 `?page=1` 变成 `?page=2`，页面整页重渲染，既没有 JS 翻页按钮、也不需要逆向接口。这类站用 `pagination-url` 最干净：

```yaml
listTraversal:
  strategy: pagination-url
  urlTemplate: "?page={page}"      # 三种写法任选：
                                  #   完整 URL： https://x.com/list?page={page}
                                  #   查询串后缀： ?page={page}（合并进 startUrl 的 query）
                                  #   绝对路径：   /c/{page}（取 startUrl 的 origin）
  maxPages: 50                     # 最大翻页数；本页解析出 0 条即视为末页、提前停止
  pageStart: 1                    # 可选，起始页码（部分站从 0 或 2 起算）
```

- `urlTemplate` 必填，且必须含 `{page}` 占位符。
- 拼装基准是**该 section 的第一个 `startUrl`**；模板三种写法见上，查询串后缀会自动合并进 base 的 query（同名参数覆盖）。
- 终止条件：翻到 `maxPages`、或某页回调返回 `0` 条、或某页抓取抛错（仅终止翻页，不整轮失败）。
- **不需要浏览器**，因此 `fallbackToUi` / `nextSelector` 对该策略无意义（可省略）。
- 列表阶段抽到的 `detailUrl` 会相对「当前页 URL」做绝对化（`absoluteUrl`），多页场景也正确。

## 5.5 新增 / 调整一个站点的标准流程

```
1. 拿到品类链接（来自 seeds.json / Excel 种子）
2. 打开页面，判断结构：
   - 规整 → 写 config/sites/<domain>.yaml（首选，零代码）
   - 复杂 → 写 packages/crawler/src/adapters/<domain>.ts（实现 SiteAdapter）
3. 跑单站 dry-run：只爬该品类前 2 页，检查提取字段是否齐全
4. 字段缺失/错乱 → 调 YAML 选择器 或 模型兜底；确认 OK 后纳入正式批次
5. 站点改版 → 优先改 YAML；大面积失效 → 切 model-generic 兜底并告警
```

## 5.6 统一兜底字段 `row` 的约定

- 适配器解析时，**显式声明的字段**进结构化列（name/specs/introMedia/cloneNumber/applications…）。
- **未声明但页面存在的字段**全部塞进 `row`（JSON 对象），命名尽量保留原站 key。
- 好处：即使今天没想到的字段，明天也能从 `row` 里挖出来做分析，不必重爬。
- 风险：不同站 `row` 结构不同——下游分析时先 `schema` 探测，再决定取哪些键（见 08）。

## 5.7 多品类 / 多栏目归属处理

**多品类**：同一产品可能出现在多个 *品类*(category，Excel 来源)（如某抗体既在"一抗"又在"流式抗体"）。按 03.4 的组合唯一索引，它只会落一行（`category_id` 记最近归属）。若业务需要"保留多品类从属关系"，见 09.4 的 `product_categories` 关联表扩展方案。

**多栏目**：同一产品也可能出现在多个 *栏目*(section，站点抓取规则维度)（如"全部产品"和"促销"）。此时按**去重口径 B**：`section_key` 已并入唯一键，同 SKU 在不同栏目**分开为两条**（适合"同 SKU 在不同栏目详情内容确实不同"）。配置写法见 5.3.2。

> 二者区别：`category` 是"我们想去爬哪些品类"（种子源），`section` 是"同一品类里按哪套规则抓"（抓取规则）。互不替代。
