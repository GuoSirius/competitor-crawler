# 05 · 站点接入指南

> 本篇回答"**每个站列表/详情页都不一样，怎么统一、后期怎么调**"。这是长期维护项目的关键：新增/调整一个站点应尽量只改配置，不动核心代码。

## 5.1 业务视角：为什么要"适配器"

24 个站点、上百个品类页，**结构各不相同**：

- 有的列表整页分页（点页码整页刷新），有的无限滚动（边滚边加载）；
- 有的详情页是静态 HTML（cheerio 可直接解析），有的靠 JS 渲染、甚至有签名/加密/风控接口；
- 字段命名天差地别（"克隆号 / Clone / mAb" 同指一物）。

若把解析逻辑硬写在核心流水线里，每加一个站都要改代码，且一处改版全局受影响。我们用**适配器（Adapter）边界归一化**解决：每个站只产出统一的 `NormalizedProduct`，下游完全不感知差异。

## 5.2 统一接口：SiteAdapter

所有站点实现同一接口，对外屏蔽差异：

```ts
interface SiteAdapter {
  /** 站点域名（用于 Registry 路由） */
  match(url: string): boolean;

  /** 列表遍历：返回该产品品类下全部产品详情页 URL（或带上下文的对象） */
  listTraversal(page: PageHandle): Promise<ListItem[]>;

  /** 解析列表页单条 → 抽取详情页链接 + 基础字段 */
  parseList(node: NodeHandle): ListItem;

  /** 解析详情页 → 归一化产品（含 specs / introMedia / cloneNumber / applications / row） */
  parseDetail(page: PageHandle): NormalizedProduct;
}
```

- `PageHandle` 是 Fetch 层给适配器的"页面句柄"：内部是 Playwright Page（渲染后的 DOM + 截图），对适配器暴露 `html()` / `screenshot()` / `click()` / `scroll()` / `waitFor()`。
- 适配器**不关心**怎么翻页网络细节，只声明"我要点下一页 / 要滚到底"，由 Fetch 层执行。

## 5.3 三类适配器 + 模型通用兜底

| 适配器类型 | 何时用 | 维护成本 |
|---|---|---|
| **配置 YAML 适配器** | 结构稳定、字段位置固定的站点 | 最低：改 `config/sites/*.yaml` 即可 |
| **代码 Adapter** | 结构复杂、需自定义逻辑的站点 | 中：写一个实现 `SiteAdapter` 的类 |
| **模型通用适配器（兜底）** | 以上都搞不定时，直接让模型读页面提取 | 低但耗 token：作为最后手段 |

路由优先级：`YAML 配置` → `代码 Adapter` → `模型通用适配器`。模型兜底保证"没有写适配器的站也不会整轮失败"。

### 5.3.1 配置 YAML 适配器示例

```yaml
# config/sites/abcam.yaml
domain: abcam.com
listTraversal:
  strategy: pagination-html      # 翻页策略（见 5.4）
  nextSelector: "a.pagination-next"
  maxPages: 50
parseList:
  itemSelector: "div.product-card"
  fields:
    detailUrl: { sel: "a.product-link", attr: href }
    name:      { sel: "h3.product-name", text: true }
parseDetail:
  fields:
    name:          { sel: ".pd-name", text: true }
    cloneNumber:   { sel: ".clone-no", text: true }
    applications:  { sel: ".app-list li", list: true }
    specs:         { sel: ".spec-row", list: true,
                     map: { spec: ".spec", priceNow: ".price-now",
                            priceActivity: ".price-act", pricePromo: ".price-promo" } }
    introMedia:    { sel: ".intro-block", list: true,
                     map: { image: "img@src", description: ".intro-desc" } }
  # 其余未列字段 → 自动全量进 row（兜底）
  captureRest: true
```

- 新增一个"结构规整"的站点：复制模板、改选择器即可，**无需写代码、无需重启（热加载配置）**。
- `captureRest: true` 保证"页面其余所有信息统一进 `row`"，契合用户"其余全量兜底"要求。

### 5.3.2 模型通用适配器（兜底）

当某站没有 YAML / 代码适配器，或既有的突然大面积失效（疑似改版）：
- 抓取页面可见文本 + 截图 → 调模型（见 04 提取契约）→ 输出 `NormalizedProduct`。
- 适合加密/风控/JS 重渲染站（直接读"用户所见"，天然绕开逆向）。
- 代价是 token 消耗；因此作为**兜底**而非首选。

## 5.4 翻页四种遍历策略（对应 03.6）

统一在 `listTraversal.strategy` 声明，Fetch 层据此驱动浏览器：

| 策略 | 行为 | 备注 |
|---|---|---|
| `pagination-html` | 点击页码链接 → 整页重渲染 → 解析 | 最常见，纯 UI 驱动 |
| `pagination-api` | 点击触发 XHR，监听 network 取 JSON（可选优化） | 仅稳定无签名站启用；失败自动回退 html |
| `scroll-api` | 滚动到底加载更多（无限滚动） | 同上，可优化为直接调滚动接口 |
| `model-generic` | 模型读页面判断"有没有下一页/加载更多按钮"并操作 | 极端异构站的兜底 |

> **用户最新要求落地**：默认**优先用浏览器渲染内容，不主动逆向接口**。接口模式只是可选优化（稳定、无签名、无风控时），且配置 `fallbackToUi: true` 确保失败回退 UI 驱动。定位不到翻页接口时发 `NEEDS_API_HINT` 告警（见 07），由你人工找到后回填，再告知系统。

## 5.5 新增 / 调整一个站点的标准流程

```
1. 拿到品类链接（来自 seeds.json / Excel 种子）
2. 打开页面，判断结构：
   - 规整 → 写 config/sites/<domain>.yaml（首选，零代码）
   - 复杂 → 写 packages/crawler/src/adapters/<domain>.ts（实现 SiteAdapter）
3. 跑单站 dry-run：只爬该品类前 2 页，检查提取字段是否齐全
4. 字段缺失/错乱 → 调 YAML 选择器 或 模型兜底；确认 OK 后纳入正式批次
5. 站点改版 → 优先改 YAML；大面积失效 → 切 model-generic 兜底并告警
```

## 5.6 统一兜底字段 `row` 的约定

- 适配器解析时，**显式声明的字段**进结构化列（name/specs/introMedia/cloneNumber/applications…）。
- **未声明但页面存在的字段**全部塞进 `row`（JSON 对象），命名尽量保留原站 key。
- 好处：即使今天没想到的字段，明天也能从 `row` 里挖出来做分析，不必重爬。
- 风险：不同站 `row` 结构不同——下游分析时先 `schema` 探测，再决定取哪些键（见 08）。

## 5.7 多品类归属处理

同一产品可能出现在多个品类（如某抗体既在"一抗"又在"流式抗体"）。按 03.4 的组合唯一索引，它只会落一行（`category_id` 记最近归属）。若业务需要"保留多品类从属关系"，见 09.4 的 `product_categories` 关联表扩展方案。
