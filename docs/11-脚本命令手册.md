# 11 · 脚本命令手册（统一维护，单一真相源）

> 本文件是**全部可执行脚本的唯一真相源（single source of truth）**。新增 / 修改任何脚本，必须同步更新本文件，并在**根 `package.json`** 保留对应入口（避免频繁切换工作目录）。每条脚本标注：所在包、作用、用法、适用场景。

## 11.1 约定

- **根优先**：所有脚本在根 `package.json` 都有入口，统一 `pnpm <script>` 触发，不必 `cd` 进子包。
- **子包兜底**：各子包 `package.json` 保留自身实现（便于单独调试），但根必须镜像。
- **命名**：子包同名脚本根直接复用同名；web 的 `dev` / `build` 在根为 `dev:web` / `build:web`（避免与根潜在冲突）。
- **登记**：新增脚本 → 子包加实现 → 根加入口 → 本文件 §11.x 补一行。

## 11.4 抓取与站点接入

### `crawl`
- 包：crawler（根同名 `pnpm crawl`）
- 作用：全量增量爬取。流程：按数据源确定站点范围 → 逐站点 `sections` 选栏目 → 列表翻页（给条目打 `sectionKey`）→ 详情解析归一化 → upsert（冲突键 `(company_id, identity_key, section_key)`，去重口径 B）→ 软删（连续 2 轮缺失才 `delisted`）；每轮记 `crawls` 批次
- 爬取范围数据源（可切换）：
  - `--source config`（**默认**）：扫描 `config/sites/*.yaml` 作为范围真相源（YAML 是唯一真相源），自动按 YAML 的 `company` 字段（缺省回退域名）upsert 公司——website 命中域名或 name 命中公司名（含人工手动插入的行）则复用，website 为空时自动补全；按 `categoryPath`/`category` + `productLine` 建分类树；配了 `categoryFromPage` 的站点按详情页面包屑**动态建分类**（见 05 §5.5）
  - `--source seeds`：读库内 `categories`（种子 Excel 经 `seed` 入库）。Excel 已降级为**一次性初始化导入工具**，日常不用（`--dry-run` 下公司/品类写入降级为仅预览）
- YAML 与代码适配器是**加性**关系（决策A 已修订）：`config/sites/<domain>.yaml` 与 `packages/crawler/src/adapters/<domain>.ts` **可共存**，共存时**正常抓取**、不跳过——YAML 是主力，代码适配器只补 YAML 表达不了的钩子（过 WAF / 自定义分页 / 解析后补字段）。跑完仅打印一行「N 个站点挂有代码适配器（钩子生效）」供确认。详见 [05-站点接入指南 §5.3](05-站点接入指南.md)
- 用法：
  - `pnpm crawl` 全量（默认 config 源 = `config/sites/*.yaml` 全部站点）
  - `pnpm crawl --source seeds` 一次性场景：按种子 Excel 入库的范围跑
  - `pnpm crawl --domain <domain>` 仅爬指定站点，逗号分隔多个（调试 / 少数站补跑）。**站点标识统一 `--domain`**（等价旧名 `--site`，仍可用；`probe`/`gen-site` 本就写 `--domain`）
  - `pnpm crawl --section <key>` 仅爬指定栏目（逗号分隔多个；多规则站点用 `sections[].key`）
  - `pnpm crawl --category <名>` 仅爬品类名子串命中的栏目（不区分大小写）
  - `pnpm crawl --product-line <线>` 仅爬指定产品线（`seeds` 模式按 categories.product_line 过滤；`config` 模式按 YAML `sections[].productLine` 过滤，未声明产品线的栏目排除）
  - `pnpm crawl --dry-run --max-pages 2 --limit 5` 只爬前 2 页、每栏目最多 5 条详情、**完全不写库**（接站点前验证）：不插 `crawls` 运行记录、产品不 upsert、`--source config` 的公司/品类 upsert 也降级为仅预览（打印「将新建/将更新」），全程零写入
  - 翻页 / 条数参数（`--max-pages` 与 YAML `maxPages` 取小，缺省上限 1000；**数量用 max-pages，页码用 page-start，别混**）：

    | 规范名 | 语义 | 旧名（仍可用） |
    |--------|------|---------------|
    | `--max-pages <n>` | **最多抓几页**（数量护栏，与 YAML `maxPages` 取小） | `--pages` |
    | `--page-start <n>` | **从第几页开始**（页码起点） | — |
    | `--page-end <n>` | 到第几页（闭区间，仅 pagination-url） | — |
    | `--page-offset <n>` | 每页条目起始偏移（覆盖 YAML `offset`，所有策略生效） | `--offset` |
    | `--page-size <n>` | 每页最多条数（覆盖 YAML `limit`） | `--per-page` |
    | `--limit <n>` | 详情阶段**总条目**上限（与 `--page-size` 不同：后者是每页条数） | — |

    例：`--page-start 2 --page-end 5`（仅 pagination-url，覆盖 YAML pageStart/pageEnd）+ `--page-offset 10 --page-size 20`（每页跳过前 10 条、连取 20 条）。section 的 `listTraversal` 与顶层**字段级合并**。纯列表无翻页的栏目**不要配 listTraversal**——`pagination-html` 无 `nextSelector` 时点击下一页失败即自然终止在第 1 页。
  - `pnpm crawl --render ssr|browser|auto` 指定渲染模式（默认 auto：静态内容偏少自动回退 Playwright）
  - **Hybrid 渲染**：站点/栏目级 YAML 可写 `renderList` / `renderDetail` 分别指定列表页与详情页模式（回退链 renderList → render → 顶层 render → auto；见 10.3 渲染模式写入 YAML 说明）
  - `pnpm crawl --resume [<断点文件>]` **断点续跑**：长跑中断后从断点恢复——不带值自动取 `.crawl-state/` 最新断点。已完成栏目整段跳过（不重抓不重写）、已落库产品详情不重抓（只刷新新条目）。整轮失败时命令行会直接打印续跑命令，断点保留在 `.crawl-state/`（成功轮自动清理）
- 场景：季度主任务
- 失败隔离：单站 / 单条 / 单栏目抓取失败只计 `failed` 并继续，不整轮失败
- 规模化兜底（大站点数万~十几万条）：
  - **列表页失败重试**：单页抓取失败自动重试（YAML `listTraversal.listRetry`，默认 1），重试耗尽跳过该页继续翻页并记入缺失页清单（汇总告警，不再静默截断整轮）
  - **增量批量落库**：按 `CRAWL_UPSERT_BATCH`（默认 200）分批 upsert，价格历史多行一次写入；MySQL/PG 整批包 1 个事务（仅 1 次 commit）
  - **断点续跑**：见上文 `--resume`；中断即存进度 + 落 `CRAWL_INTERRUPTED` 告警

### `schedule`
- 包：crawler（根同名 `pnpm schedule`）
- 作用：定时跑爬取并把本轮结果（新增 / 更新 / 下架 / 失败 / 待处理告警数）推送到**告警通道**（企微 / 钉钉 webhook，见 `.env.example` 的 `ALERT_*_WEBHOOK`）
- 用法：
  - `pnpm schedule` 立即跑一次（等价于 `pnpm crawl --source config` + 推送）
  - `pnpm schedule --daemon` 启动守护进程，按**季度首月 1 日 03:00** 自动触发（Ctrl+C 退出）；等价于系统级 cron / Windows 任务计划
- 失败隔离：爬取失败会抛错中断；推送失败只记日志不阻断
- 场景：服务器上长期运行，替代人工季度爬取；配合 `pnpm dev:web` 让团队随时看最新数据
- 详见：[06-运行与调度 §6.4](06-运行与调度.md)

### `probe`
- 包：crawler（根同名 `pnpm probe`）
- 作用：单站验证，抽测 YAML 适配器解析是否正确（先验证再批量）；并**抽查详情页自动判定「规格×价格形态」**（docs/05 §5.3.4）
- 用法：`pnpm probe --domain <domain> [--list-url <url>] [--section <key>] [--render auto|ssr|browser] [--sample 5] [--detail 1]`
- 必填：`--domain`（对应 `config/sites/<domain>.yaml`）；`--list-url` 缺省时取栏目的 `startUrls` / YAML `startUrl`
- `--section`：多规则站点只验证指定栏目（`sections[].key`）；省略则遍历全部栏目
- `--detail`：每栏目抽查几个详情页做形态探测（默认 1；`--detail 0` 关闭）
- 配置不完整（身份桩缺 `parseList`）：打印友好告警并**正常退出（exit 0）**，提示先跑 `gen-site` 补全，不抛堆栈、无 pnpm 报错横幅
- 形态探测行为：
  - A/B/C → 打印「静态可抽」+ **可直接粘贴的 YAML 片段**
  - D/E → 打印**「在哪配、怎么配」的完整步骤**，并写入 `alerts`（`type=NEEDS_API_HINT`，幂等不重复）
  - 已配 `parseDetail.api` → 跳过形态提示，**实测接口**并打印「取到 N 条」+ 首条样本
- 场景：新增 / 改站点前（多规则站点逐栏目验证）
- 详见：[10-验证与配置生成工具](10-验证与配置生成工具.md#102-probe--单站验证)、[05-站点接入指南 §5.3.4](05-站点接入指南.md)

### `gen-site`
- 包：crawler（根同名 `pnpm gen-site`）
- 作用：模型驱动生成站点 YAML 配置（抓取页面 → 调模型 temp=0 → 产出 `config/sites/<domain>.yaml`）
- 用法：`pnpm gen-site --domain <d> [--list-url <u>] [--detail-url <u>] [--company-key <k>] [--render auto] [--notes "..."]`
- 必填：`--domain`；`--list-url` 可选（已有 YAML 桩写明 `startUrl` 时自动复用，CLI 传入优先）
- 场景：新增站点；产出后 `pnpm probe` 验证
- 备注：`--company-key` 会写入产出 YAML 的 `company` 字段，作为 `crawl --source config`（默认）下归属公司名（缺省按域名兜底）
- 产出回验：模型产出自动在真实 HTML 上校验——硬伤（列表 0 条 / pagination-url 缺 urlTemplate）打回重试 ≤2 轮、仍不过**拒写盘**；详情字段未命中则写 `# ⚠️ TODO` 文件头注释。定位=草稿生成器，标准流程 `gen-site → probe → 修正`
- 详见：[10-验证与配置生成工具](10-验证与配置生成工具.md#103-gen-site--模型驱动生成配置)

### `gen-site:template`
- 包：crawler（根 `pnpm gen-site:template`）
- 作用：生成「批量站点配置」Excel 模板（含表头 + 示例行 + 填写说明页），默认落 `data/seeds/gen-site-template.xlsx`
- 用法：
  - `pnpm gen-site:template`（默认路径）
  - `pnpm gen-site:template --file <路径>`（自定义输出）
- 场景：有**一批**站点要生成配置时，先生成模板、填好后用 `gen-site:batch` 一次性批量生成（替代逐个 `gen-site`）
- 列：`域名(domain)` / `列表页URL(listUrl)`（必填）、`详情页URL(detailUrl)` / `公司(companyKey)` / `渲染(render)` / `备注(notes)`（可选）
- 详见：[10-验证与配置生成工具 §10.4](10-验证与配置生成工具.md#104-gen-sitetemplate--批量生成-excel-模板)

### `gen-site:batch`
- 包：crawler（根 `pnpm gen-site:batch`）
- 作用：读取批量表 → 逐行调用 `genSite`（模型驱动）生成 `config/sites/<domain>.yaml`；**失败隔离**（单行失败只计失败并继续）
- 用法：
  - `pnpm gen-site:batch`（默认读 `data/seeds/gen-site-template.xlsx`，与模板输出同文件）
  - `pnpm gen-site:batch --file <路径>`（指定其它 Excel）
  - `pnpm gen-site:batch --dry-run`（仅解析并打印待生成清单，不调模型、不落盘）
- 场景：批量新增站点；先用 `gen-site:template` 填表，再本命令一次性生成
- 列识别按表头关键字（domain/域名、listUrl/列表页、detailUrl/详情页、companyKey/公司、render/渲染、notes/备注），大小写不敏感
- 详见：[10-验证与配置生成工具 §10.5](10-验证与配置生成工具.md#105-gen-sitebatch--批量生成站点配置)

- 作用：字段晋升回填（把 `row` JSON 中某字段值回填到已新建的独立列）
- 用法：`pnpm backfill --column <col> --row-key <key> [--dry]`
- 场景：后期把重要字段晋升为独立列后，回填历史数据（幂等，可反复跑）

### `validate`
- 包：crawler（根同名 `pnpm validate`）
- 作用：站点配置**字段校验**（Q1）——按字段注册表（`shared/src/adapter/fieldRegistry.ts`）检查各站点 YAML：缺必填（name/title）/缺身份键 → error；未知字段疑似拼写（如 `productName` → `name`）→ warn；阶段错位 / 数值未标 `number: true` / 配置桩 → info
- 用法：`pnpm validate [--domain <domain>]`（`--domain` 等价旧名 `--site`）；省略则校验 `config/sites` 下全部站点；存在 error 级问题时**退出码 1**（CI 门禁用）
- 参数速查：`pnpm <cmd> --help` 分组打印（通用 / 翻页 / 各命令专属），不再靠记忆 long usage 行
- 关键设计：**不阻断**——probe/crawl 加载配置后自动跑同样校验但仅打印提示，照常继续；未知字段默认视为合法站点特有字段（进 `row`），只对「疑似拼写错误」告警，宁漏勿误
- 详见：[05-站点接入指南](05-站点接入指南.md)

### `field-docs`
- 包：crawler（根同名 `pnpm field-docs`）
- 作用：打印**内建字段字典**——products / contents 各字段名、**落库列**、类型、阶段（list/detail/both/site）、是否必填/身份键、是否参与列表兜底合并与不一致审计
- 用法：
  - `pnpm field-docs` → 打印 products / contents 两张字典表（含「落库列」列）
  - `pnpm field-docs --domain <domain>`（`--site` 等价）→ 在上两张表之后，**额外打印该站点按栏目的「YAML 字段 → 落库列」对照**，并列出「未配（该列暂无数据）」的字段
- 场景：写 YAML 时不知道该配哪些字段名（如「产品名是 name 还是 productName」）先查它；或者直接看「我这个站点哪一列目前是空的、该配哪个字段」
- 映射规则（`dbColumnOf`，见 `shared/src/adapter/fieldRegistry.ts`）：
  | 情况 | 打印 | 说明 |
  |---|---|---|
  | 字段名与列名同名（YAML `summary` → 列 `summary`） | `summary` | 只写一个即可 |
  | camelCase 转 snake_case（YAML `bodyHtml` → 列 `body_html`） | `body_html` | 不一致 → 两列都写 |
  | contents 管线配 `name` | `title` | 引擎 `np.name` → `title` 列，建议 contents 栏目 YAML 写 `name` |
  | 注册表未登记（`cover` / `种属` 等站点特有） | `row（兜底）` | 只进 `row` JSON，不成独立列 |
  | 站点级配置字段（stage=site） | `—` | 非解析字段，不落列 |

### `sweep`
- 包：crawler（根同名 `pnpm sweep`）
- 作用：**批量反爬复探**——对 docs/14 C 类（WAF 拦截）站点逐个试抓，不依赖站点 YAML，只测「可达性 + 挑战页识别 + 内容量」，为站点升级/降级提供证据。挑战页（Cloudflare/阿里云盾/Imperva/reCAPTCHA…）会显式报 `CHALLENGED[kind]` 而不是被当成空栏目
- 用法：
  - `pnpm sweep --group c` → 预设 C 类全集（按公司名关键词从 `data/seeds/crawl-inventory.json` 匹配，每站取首页+第一个产品 URL）
  - `pnpm sweep --domain <d> --url <u>` → 单站单 URL
  - `--mode ssr|browser|both`（默认 both：每站先 ssr 再 browser 各一轮）、`--limit N`（只跑前 N 站，冒烟）、`--headless true`（默认有头，更隐蔽）
  - 有头模式默认**窗口最大化铺满屏幕**（`antiBot.maximize`，默认 true；视口跟随真实屏幕，不再覆写 1920×1080）。需要固定小视口调试时可在站点 YAML 写 `antiBot: { maximize: false }`
- 输出：控制台逐行 + 报告落盘 `data/seeds/sweep-<时间戳>.md`（结果表 + 判读说明）
- **与 `diagnose` 的分工**：`sweep` 是**批量广度**（一次几十站、只测三件事、结论粗）；**单站要下结论、或和用户对不上时用 `diagnose`**（见 §11.4.1），它给的是可复现的对照表而不是一句话。

### 11.4.1 `diagnose`（反爬归因，单站下结论用）

- 包：crawler（根同名 `pnpm diagnose`）
- 作用：**回答「这个站到底是拦我、还是我姿势不对」**——同一 URL 依次走多套浏览器通道，把每套的 HTTP 状态 / 正文长度 / 挑战页命中 / 产品锚点数 / 耗时摊成一张对照表，再附「指纹体检」与一句可直接照做的处置建议。零副作用：只读页面，不落库、不写站点配置
- **为什么需要它**：2026-10-05 之前「代码说被 WAF 拦、用户说浏览器能开」只能靠各执一词。现已把判断固化成命令，任何人任何时候都能一条命令复现同一张表
- 用法：
  - `pnpm diagnose --domain <d>` → 默认跑 5 套通道对照 + 指纹体检（URL 自动取该站 YAML 的栏目入口）
  - `--url <u>` → 指定被测 URL（不取 YAML）
  - `--mode <通道[,通道…]>` → 只跑指定通道，逗号分隔。可选：`ssr` / `chromium-headless` / `chromium-headful` / `chrome-headful` / `chrome-headless` / `cdp:<url>`
  - `--rounds <n>` → 命中 Cloudflare 托管挑战时额外重试 n 轮（**每轮带 cookie 重新导航**，不是原地干等）
  - `--no-fingerprint` → 跳过指纹体检（批量排查时省一次开窗）
  - `--json` → 机器可读输出
- 通道对照表怎么读（判读顺序即 `conclude()` 的判定顺序）：

  | 现象 | 结论 | 下一步 |
  |---|---|---|
  | 部分通道 200、部分失败 | **姿势问题** | 把通的通道姿势写进站点 YAML `antiBot`，不是封锁 |
  | 全 403 且文案是 `Attention Required! \| Cloudflare` | **IP 级封禁** | 换出口 IP（YAML 站点级 `proxy: '${CRAWL_PROXY}'`）或放弃；改指纹无效 |
  | 全 403/503 且命中 `cf-mitigated: challenge` / `Just a moment…` | **托管挑战未过** | 调大 `CRAWL_CHALLENGE_ROUNDS` / `CRAWL_CHALLENGE_WAIT_MS`；确认走有头；仍不过再换 IP |
  | 全 `ERR_CONNECTION_*` / 超时 | **网络层** | 查 DNS/证书/出口；用 `cdp:` 连自己 Chrome 复现「用户视角」 |
  | 状态码 200 但 items=0 | 拿到壳 | 换入口/下钻（见 docs/14 B 类） |

- **`cdp:` 通道**（最硬的证据）：`--mode 'cdp:http://127.0.0.1:9222'`。需先自己开一个带调试端口的 Chrome：
  - Windows：`"C:\Program Files\Google\Chrome\Application\chrome.exe" --remote-debugging-port=9222 --user-data-dir="%TEMP%\cdp-profile"`
  - 在那个窗口里**人工过完盾**再跑本命令 —— 带的就是你已过盾的会话，100% 复现你的视角
  - 该通道只断开连接，**不会关掉你的窗口**
- 会话复用：与正式抓取共用同一份 `.runtime/state/<host>.json`（人工过盾成果）。已过盾的站 diagnose 不会因「没带 cookie」误报 403
- 相关环境变量：`CRAWL_CHALLENGE_ROUNDS`（自动放行轮数，默认 8）、`CRAWL_CHALLENGE_WAIT_MS`（每轮间隔，默认 6000）、`CRAWL_INTERACTIVE`（是否等人工过盾，默认 true）

## 11.5 下游与前端

### `report`
- 包：crawler（根同名 `pnpm report`）
- 作用：生成下游交付物（Excel 导出 / 图表）

## 11.6 环境与质量

### `playwright:install`
- 包：crawler（封装）
- 根入口：`pnpm playwright:install`
- 作用：安装 Playwright 浏览器内核（root 下 playwright 无二进制，故委托 crawler 包执行）
- 用法：`pnpm playwright:install`
- 场景：首次安装 / 升级 Playwright 后

### `typecheck`
- 包：全仓（`node scripts/typecheck.mjs`，依次 shared → crawler → web）
- 根入口：`pnpm typecheck`（**唯一入口**，自动纳管 web）；`pnpm typecheck:web`（仅 web，等价 `nuxt typecheck`）；`pnpm typecheck:all`（与 `pnpm typecheck` 同义）
- 作用：TypeScript 类型检查
- 场景：CI 与提交前（依赖安装后）
- **web 门禁自适应**：脚本检测 `packages/web/node_modules/vue-tsc` 是否存在——
  - 未安装（还没 `pnpm install`）→ 提示跳过，只校验 shared + crawler，门禁**不会变红**；
  - 已安装 → 自动跑 `nuxt typecheck`（内部先生成 `.nuxt/` 类型）。
  所以给 web 加依赖后**只需 `pnpm install`**，无需改脚本 / CI。详见 [12-工程规范 §12.9](12-工程规范.md)。
- ⚠️ 往 `packages/web/package.json` 增删依赖后，`pnpm-lock.yaml` 必须同步更新并提交，否则 CI 的 `--frozen-lockfile` 会失败。

### `test`
- 包：根
- 作用：跑单元测试（vitest，68 例：抽取层 FieldSpec / 形态探测 / 配置归一化 / URL 去重 / 模型配置解析 / **环境变量契约**）
- 用法：`pnpm test`（单次，CI 用）；`pnpm test:watch`（开发时监听）
- 用例位置：**与源码同目录**（`packages/*/src/**/*.test.ts`），见 [12-工程规范 §12.10](12-工程规范.md)
- ⚠️ `envContract.test.ts` 会校验「`process.env` 读取点 ↔ `.env.example` 声明」双向一致，**写错变量名会直接失败**（见 [12-工程规范 §12.13](12-工程规范.md)）
- 场景：提交前门禁、CI

### `hooks:install`
- 包：根（脚本 `scripts/install-hooks.mjs`）
- 作用：安装**回退版**git 钩子到 `.git/cph/`（幂等）。首选是 husky（`pnpm install` 时由 `prepare` 自动启用）；此回退用于 husky 包装脚本在本机 PATH 下不可用时
- 用法：`pnpm hooks:install`，之后用 `git -c core.hooksPath=.git/cph commit -m "feat: ..."`
- ⚠️ 两条路径**门禁强度完全相同**（都调用同一份 `scripts/precommit.mjs` / `scripts/commitmsg.mjs`），不存在「换 hooksPath 就绕过」
- 场景：换电脑 / 钩子丢失后重建

### `commitlint`
- 包：根
- 作用：校验提交信息符合 Conventional Commits；提交时由 **pre-commit/commit-msg 钩子**自动跑（husky 或 `.git/cph`）
- 用法：`pnpm commitlint --from=HEAD~1`
- ⚠️ 两条硬约束（踩过）：`type` 必须是标准枚举（无 `config`，用 `chore`）；**主题不能以大写单词开头**（`FieldSpec 支持…` 会被 `subject-case` 拒绝）
- 场景：提交前自查 / CI 校验

## 11.7 版本与 Changelog

### `release`
- 包：根（脚本 `scripts/release.mjs`）
- 作用：standard-version 自动 bump 版本 + 写 `CHANGELOG.md` + 打 `vX.Y.Z` 标签并提交
- 用法（**只此一个脚本**，运行时选择类型）：
  - `pnpm release` → 交互式询问 patch / minor / major
  - `pnpm release major` → 直接指定类型（非交互，便于 CI / 一键；当前 0.1.0 → 切 1.0.0）
- 场景：发布版本（打标签后由你手动 `git push --follow-tags`）

### `changelog` / `changelog:rebuild`
- 包：根
- 作用：`changelog` 走 standard-version 增量生成（受 `.versionrc.json` 全量 types 控制，feat/fix/refactor/docs/test/ci 等全部类型都会入账）；`changelog:rebuild` 按全部 git tag 全量重建 `CHANGELOG.md`（changelogen 风格：## vX.Y.Z + emoji 双语分组），**每次 release 后建议重跑一次**以统一历史格式
- 用法：`pnpm changelog` / `pnpm changelog:rebuild`（`-- --dry-run` 只预览）
